# 技能设计与取舍

版本：0.4.0；2026-10-25。

## 目标及边界

目标是让读者准确理解内容，知道结论为什么成立，并在需要行动时知道怎么做。用户提出的优先关系是：先有逻辑、清楚、完整，再尽量简洁。准确性是始终要守住的条件。

技能支持实质性文字输出，包括直接回复、文档、注释、交接与可见分析摘要。它不改变任务权限，不代替领域核验，也不把所有输出变成教程。创作、精确引用、固定格式和专业受众应按任务要求适配。

## 主要决策

### D01：把问题清单与运行规则分开

问题清单保存在 `doc/problems.md`，供开发和评测使用。入口只保留会改变写作决策的规则。这样 agent 不必每次加载完整调研，也避免照着问题清单写出冗长的自检报告。

### D02：按理解关系组织，而不是固定格式

默认尽早给答案，但如果某个前提必须先交代，就先交代。列表、表格、标题按信息关系选择，不规定“三段式”“必须有总结”。这处理 P01–P08、P29–P30，也防止统一风格演变为模板化。

### D03：术语的价值和解释成本一起判断

不建立普遍的简单术语名单。同一个“缓存”，对开发者可以直接用，对新手可能需要解释。保留有助于精确交流、后续学习和检索的标准名称；解释放在第一次需要理解的位置，达到当前任务所需的深度即可。

短语只出现一次且标签本身没有后续价值，可以直接说明含义。术语解释后正常使用，避免每次都绕成长句。对应 P09–P16。

### D04：压缩的是重复，保留的是含义

清晰与简洁冲突时，优先保留关键关系、条件、范围与例外。明确字数限制仍需遵守：选择最重要的信息，删扩展知识；若无法容纳任务全部要求，应说明冲突，而不是默默改变结论。对应 P17–P22、P33。

### D05：比喻需要有具体用途

默认直接解释，必要时使用领域内的小例子。比喻只在能解决理解障碍或用户要求时采用，并回到实际机制。不会禁用文学任务中的修辞。对应 P23–P24。

### D06：统一质量，不统一所有表面风格

统一逻辑、证据边界、术语处理、克制语气和状态表达。保留语言、文体、篇幅、知识深度和合理个性。规则不能覆盖用户的明确要求；不同模型是否因此更一致，必须通过同题比较验证。对应 P26–P30、P38–P42。

### D07：不给技能附加“提升智力”的承诺

清楚的工作记录可能有助于交接、发现遗漏和后续任务，但这不等同于改变模型内部推理能力。只评估可观察输出和任务结果；不索要或保存内部思维链。对应 P41，研究边界见 R4。

### D08：具体化不得新增事实

“写具体”很容易诱发虚构数字、执行状态或个人经历。入口明确限制事实增补，示例明确给定前提；缺少信息时承认缺少，不替原作者发明理由。对应 P31–P37、P40。

### D09：默认适用，按复杂度投入

用户补充要求：具体步骤有助于执行，但不能让基础沟通技能挤占实际工作的时间和 token。采用“短答直接写并检查关键处；复杂内容整理、成文、定点修正”的方案。触发复杂处理的依据是遗漏与理解风险，不是每次都完整走流程。

不要求每条消息创建任务卡、术语表、提纲文件、评分报告或自检声明。可复用已有工作材料；检查一次后只修具体缺陷，避免不断润色。步骤明确不意味着步骤必须全部外显，最终文字能否满足需求才是主要证据。

### D10：把可核验性放在交付与评测上

事实能否在材料中找到、必要条件是否保留、陌生概念是否解释，都能对照产物检查。常规使用直接检查最终产物；专门评测时再留下“要求—对应段落—发现问题—修改结果”的简短记录。记录仅是对可见草稿的编辑说明，不是隐藏思维过程。

不对内部思考设置文风、提纲或字数要求。清晰的可见交接记录可能有益于后续工作，但不能据此承诺内部推理更强。

### D11：加载与执行质量分开处理

根据 [官方 Build skills 文档](https://learn.chatgpt.com/docs/build-skills)（2026-10-24 查阅），技能既支持明确调用，也支持按描述自动选择；`allow_implicit_invocation` 默认为 true，但不代表无条件执行。本项目显式保留 true，并用根目录 `AGENTS.md` 要求每次任务应用本地技能；已有最新内容时复用。

[官方 customization 文档](https://learn.chatgpt.com/docs/customization/overview) 将常驻指令与按需技能区分。本项目据此让入口规则负责默认加载，技能负责具体写法。`skills/` 是项目的源码目录，不声称它会自动成为宿主的标准发现目录；本项目通过 `AGENTS.md` 的直接路径引用使用。跨项目安装需要目标环境的常驻规则另行引用实际路径，目前未修改全局配置。

这仍是指令层的设计，不是强制执行机制。若将来有自己的 agent 运行程序，可以在请求构造时注入精简要求，在有必要的任务完成后检查产物；那属于宿主集成，当前没有实现。重复加载完整技能或每次增加独立评审调用，不应成为默认方案。

### D12：检验收益时同时计成本

skill 文件格式本身不保证效果优于普通规则。可测试的假设是：明确的触发条件、修正动作和少量示例，可能比“讲清楚”更易执行。必须比较同内容规则与 skill 包装，避免把包装误当成提升来源；同时记录实际任务完成率、耗时、token 与调用次数。

没有零成本保证。入口占上下文，额外生成和校验也有成本；能否接受取决于真实任务收益。优先减少不必要的中间产物，不用凭空设定一个“节省百分比”来证明有效。

### D13：已有材料的维护边界

读到的文风不自动成为新内容的模板。日常维护以任务正在修改的完整语义片段为边界，在原有写作和审阅中改善，不扫描全库、不标记新旧文档。已有名称可保留并解释，语义不明不能猜着改。用户明确要求大范围改造时，才加载独立的改写参考流程。来源、例外和成本设计见 [已有材料设计](existing-material.md)，对应测试为 T32–T39。

## 需求到实现的对应

| 用户要求 | 技能中的做法 | 评测入口 |
| --- | --- | --- |
| 有逻辑、讲明白 | 问题与结论优先，明确段落关系和前提 | T01、T06、T13 |
| 不用自造黑话 | 还原为具体对象、动作和关系 | T02、T14 |
| 术语能理解又能学会 | 按上下文解释、解释后沿用 | T03、T04、T05 |
| 清楚前提下简洁 | 删重复，保留条件和证据范围 | T06、T08、T15 |
| 少用无必要的比喻 | 直接解释优先，按需要用比喻 | T07、T12 |
| 跨 agent / 模型更统一 | 相同原则和评分维度，不固定句式 | 全集及多轮测试 |
| 覆盖文档、回复和注释 | 场景内只保留必要差异 | T09、T10、T13 |
| 有助于工作记录和任务表现 | 清晰记录假设、证据、状态 | T10、T13；效果尚待实测 |

## 为什么没有增加脚本或更多技能

判断逻辑、术语解释是否适量，主要依赖语义和上下文。关键词脚本容易把合理用词误判为缺陷，因此不提供自动“AI 味评分”。多个技能会分散这套共同原则，当前采用一个英文入口，以及按输出语言选择的中英文示例文件。中文指令对照留在开发文档中，语言与同步约定见 [双语维护说明](localization.md)。

开发文档与技能物理隔离，发布只需 `skills/clear-communication/`。没有修改全局 agent 配置，也没有声称本地文件已自动影响所有模型。
