# 在已有项目中逐步改善表达

日期：2026-10-25；设计版本：0.4.0。

## 结论

默认策略是：阅读时理解内容，写作时保持清楚；原本要改哪里，就把那一小段写明白。改善范围由当前任务和语义关系决定，不由文档年龄、质量标签或全库评分决定。全面改造必须是用户选择，不能因启用了技能就自动发生。

这能逐步改善经常维护的内容，但不会自动覆盖长期没人碰的文件，也不保证文档会随着时间自然全部变好。需要全面一致性时，仍应有明确的改造任务。

## 研究依据及边界

本轮查阅以下原始研究摘要与工程指南，没有复现实验：

- [Tuning-free personalized alignment via trial-error-explain in-context learning](https://www.amazon.science/publications/tuning-free-personalized-alignment-via-trial-error-explain-in-context-learning)，NAACL 2025。研究通过上下文示例及反馈引导文本风格，支持“输入示例能影响表达”的一般判断；它没有测量本技能在差文档环境中的抵抗能力。
- [Catch Me If You Can? Not Yet](https://arxiv.org/abs/2509.14543)，Wang 等，2025。研究发现模仿程度随文体与提示方式变化，不能把上下文影响说成必然、完整的文风复制。这里不能据此估算技能会被抵消多少。
- [Google Engineering Practices: Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)。指南建议改动自成一体，区分局部清理与大规模重构。本项目借鉴其可审查性原则来界定文档改动范围；这是设计迁移，不是渐进文档改善效果的实验证据。

因此，把差文档视为可能影响生成的上下文是合理的，但不应把它当作必须预先清洗全库的理由。技能应明确材料的不同用途：事实和项目名称需要核对、保留，坏句式无需模仿。显式的文体或命名要求仍然有效，不能借“坏文风”忽视用户约定。

## 默认维护怎么做

| 当前工作 | 做法 | 不扩大到什么 |
| --- | --- | --- |
| 阅读文档回答问题 | 理解事实，用清楚的表达回答；必要时保留原名并解释 | 不修改只读材料，不先清理输入文档 |
| 更新某个说明段落 | 将变化自然写入完整句子，把该段的必要关系讲清楚 | 不因邻接章节也写得差就顺便重写 |
| 改动代码并同步相关注释 | 写清当前代码的意图和约束；核对原注释含义 | 不为了改文风重命名函数或修改执行逻辑 |
| 用户只允许改数值或保留原文 | 按限制修改；只提醒会造成实质误解的问题 | 不以默认渐进改善覆盖明确限制 |
| 用户明确要求全面改写 | 在授权范围内分批改写并核验，完成全部范围 | 不把语言改造扩展成产品行为或需求变更 |

“最小完整语义片段”通常是一句话、一个列表项、一条注释或一个短段落。它不是固定行数：只改一个词会让前后矛盾时，可以连同必要句子修改；只是觉得旁边也能写得更好时，就不扩展。若理解当前段落必须依赖全项目重命名，先保留名称并解释，而不是启动全库替换。

## 遇到已有黑话

**已有名字与坏句子不是同一种问题。** 项目里确实叫“回流舱”的队列，即使名称不直观，也可能对应控制台、日志和搜索词。可以写“回流舱（保存待重试任务的队列）”，然后沿用“回流舱”。不能擅自另起“重试中心”，使同一对象出现两个不明确的名称。

如果“完成全链路闭环赋能”实际只是指发送审核结果，就在正在改的句子中直接说明发送对象、时机和结果。这里不需要保留空泛修辞，只需保留真实内容。

如果没有依据确认“闭环”究竟是什么，不凭感觉翻译成重试、通知或审批。先使用本次任务已有事实；歧义会影响正确性时才查询相关定义或提出针对性问题。无关的含混措辞不必变成新的调查任务。

局部改名容易破坏搜索和交叉引用，所以普通维护中优先保留可识别的名称并增加必要解释；用户授权术语统一时，才制定对应关系并更新受影响引用。解释只在读者需要时出现，不给每次出现的词都加括号。

## 示例：在任务里改善，而非另开清理任务

已知原注释：`// 回流舱兜底失败态闭环，三跳归档`。已有定义确认“回流舱”是待重试队列，“跳”表示尝试次数；当前任务把最多尝试次数从三次改成四次。

在普通维护授权下，相关注释可更新为：

```text
// 失败任务进入回流舱（待重试队列）；尝试四次后仍失败则归档。
```

前提是实现确实采用“尝试四次”而非“初次失败后额外重试四次”。这类差异属于行为含义，不能为了通顺自行决定。如果用户明确只要求替换“三”为“四”，则按要求做最小修改。

同一文件另一段不相关的黑话可以保持不变。新段落与旧段落的文风暂时不同是可接受的；事实、对象和术语含义不一致则必须处理。无需额外建立“旧文档清单”或汇报本次消除了几处黑话。

## 用户要求全面改造时

日常入口只保留简短边界；明确改造时才读取技能包内的 [文档改写流程](../skills/clear-communication/references/document-revision.md)。流程使用“范围及含义确认 → 分批改写 → 意义和引用验证”，不要求每批重新批准。

先处理影响多个文件的术语定义和事实歧义，再按主题或依赖分批。批次应当可以独立审查，完成后仍能正常阅读。改变名称时检查链接、锚点、界面标签和代码引用；只改文字不等于获准改接口、需求或历史记录。生成文档要在授权范围内修改源文件，不能直接润色下次会被覆盖的生成结果。

交付说明只总结实质变化和未解决问题。用户授权全范围后，应完成全范围；不要以“渐进”为由只交付样例。

## 为什么不增加日常检查

规则由正在发生的读写动作触发：读取时不沿用坏句式，输出时正常应用沟通要求，修改时守住局部语义范围。判断直接发生在已有的写作和改动审阅中，不新增扫描、标签、计分、审批或常驻报告。

额外阅读仅限当前含义确实无法确定、且影响任务结果的情况。全面改造流程是按需参考文件，不默认加入上下文。后续测试应比较同一任务在清楚和含混材料下的结果、额外读写与耗时，确认改善没有演变为扩范围重构。
