# 持续维护

## 从失败案例开始

日常使用中的主观反馈也可以触发小幅改进，不要求每次都有可复现案例。按实际掌握的信息记录任务、相关片段、理解障碍和希望保留的内容；缺失的上下文不补造，也不把孤立片段当成可复现测试。隐去隐私、凭据和不必要的业务信息，不记录模型内部思维链。

将案例关联到 [问题清单](problems.md) 的编号；无法覆盖时再考虑新增类型。单纯“不喜欢这个词”与“这个表达妨碍理解”要区分。用户明确的个人偏好可以遵循，但不能不加说明地上升为所有任务的普遍禁令。

## 形成最小修改

先判断问题来自缺知识、缺证据、任务理解、表达还是规则冲突。写作技能不应替其他问题背书。新增规则应说明判断条件与合理例外；如果已有规则足够，优先把相关修正动作或示例写具体，不重复堆指令。

考虑修改是否会矫枉过正，例如修复术语过密不应让专家回答被迫重新科普。教学示例用于说明边界，不视作独立测试；有合适方法或需要验证效果时，再设计测试用例。

## 验证与发布

1. 运行技能结构检查，检查相对链接及包内依赖。
2. 按修改风险、可用案例与用户要求决定是否运行行为测试；小幅修订可先通过日常使用观察，不强制每次测试。
3. 观察事实保持、理解效果和篇幅，不只比较文风。主观使用感受可以指导迭代，但不能据此声称已有对照验证或量化收益。
4. 按需更新设计取舍和版本记录；新增问题类型时再更新问题清单，写明哪些检查真正执行过。
5. 仅发布 `skills/clear-communication/`，开发材料继续保留在 `doc/`。

未运行行为测试时如实记录；不以结构检查证明效果，也不把测试设为所有修订的前置条件。需要对效果或额外成本作出可验证结论时再实测。后续使用若发现退步，缩小或撤回对应修改，并保留可用反馈。

## 来源维护与版本

新增来源记录标题、作者或机构、发布日期（若可得）、访问日期、链接、证据类型、支持范围及局限。失效链接不等于结论错误；寻找原始或存档来源，并记录替换情况。不要把社区观点升级成研究结论。

建议版本约定：修正文句和链接用补丁版本；新增兼容的场景或规则用次版本；显著改变默认行为或包结构用主版本。每次发布重新检查入口长度，删除重复规则。稳定的问题编号与测试编号保留，废弃项注明原因，避免重新分配编号。

- 运行两个以上模型系列的同题比较及多轮保持测试。
- 让领域外读者检验术语理解，检查“解释了”是否真的等于“懂了”。
- 评估入口长度与遵循效果的关系，再决定是否拆分更多参考文件。

这些是迭代方向，不代表已创建定时任务或承诺后台持续运行。
