# 持续维护

## 从失败案例开始

每次改进先保存可复现案例：任务、目标读者、相关上下文、原始输出、读者哪里没懂或被误导，以及希望保留的事实和表达。隐去隐私、凭据和不必要的业务信息，不记录模型内部思维链。

将案例关联到 [问题清单](problems.md) 的编号；无法覆盖时再考虑新增类型。单纯“不喜欢这个词”与“这个表达妨碍理解”要区分。用户明确的个人偏好可以遵循，但不能不加说明地上升为所有任务的普遍禁令。

## 形成最小修改

先判断问题来自缺知识、缺证据、任务理解、表达还是规则冲突。写作技能不应替其他问题背书。新增规则应说明判断条件与合理例外；如果已有规则足够，优先改示例或补测试，不重复堆指令。

每次修改至少配一个失败用例和一个防止矫枉过正的用例，例如：修复术语过密，同时检查专家回答不会被迫重新科普。

## 验证与发布

1. 运行技能结构检查，检查相对链接及包内依赖。
2. 重跑本次相关的评测题和可能受影响的反例；重大规则变化再跑完整测试集。
3. 比较事实保持、理解效果和篇幅，不只比较文风。
4. 更新问题清单、设计取舍和版本记录，写明哪些检查真正执行过。
5. 仅发布 `skills/clear-communication/`，开发材料继续保留在 `doc/`。

若尚不能运行行为测试，明确记录“未运行”和原因，不能用结构通过替代效果证明。确认回退后恢复上一版规则，保留失败案例用于以后验证。

## 来源维护与版本

新增来源记录标题、作者或机构、发布日期（若可得）、访问日期、链接、证据类型、支持范围及局限。失效链接不等于结论错误；寻找原始或存档来源，并记录替换情况。不要把社区观点升级成研究结论。

建议版本约定：修正文句和链接用补丁版本；新增兼容的场景或规则用次版本；显著改变默认行为或包结构用主版本。每次发布重新检查入口长度，删除重复规则。稳定的问题编号与测试编号保留，废弃项注明原因，避免重新分配编号。

## 当前后续重点

- 收集真实中文 agent 输出失败案例，补足社区反馈偏英文的不足。
- 运行两个以上模型系列的同题比较及多轮保持测试。
- 让领域外读者检验术语理解，检查“解释了”是否真的等于“懂了”。
- 评估入口长度与遵循效果的关系，再决定是否拆分更多参考文件。

这些是迭代方向，不代表已创建定时任务或承诺后台持续运行。
